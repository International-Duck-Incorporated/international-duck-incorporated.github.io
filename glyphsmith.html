Good to know

🛡 Why filters struggle with this

  • Bytes ≠ glyphs. The same visible word can be many different code-point sequences; filters compare sequences.
  • Defense in depth: normalize (NFKC) → case-fold → apply the UTS #39 confusable skeleton → then match.
  • Layered pipelines (client → server → database collation) may each normalize differently, creating gaps.

⛏ Minecraft notes: what actually works in chat

  • Allowed characters: vanilla Java accepts almost everything from U+0020 up, but kicks you ("Illegal characters in chat") for § section signs and control characters. MC mode flags any output containing them.
  • Length: Java chat is capped at 256 characters client-side; many servers enforce less. Zero-width padding burns budget fast; watch the ⛏ n/256 chip on every output.
  • Rendering: most of the Basic Multilingual Plane (up to U+FFFF) renders via the built-in Unicode font, even when the blocky default font lacks a glyph. Characters above U+FFFF (squared/negative-circled capitals, supplementary variation selectors) show as □. MC mode hides those variants automatically.
  • Zero-width chars render as nothing (or hairline gaps) on current Java builds, but always test on your exact version, font and resource pack.
  • Bedrock / Realms run their own filters and may strip or normalize some tricks; results differ per platform. Always test client view and server console.

⚖ Responsible use

  • Built for security research, filter-robustness testing, education and creative typography.
  • Don't use obfuscation to harass, spam, or evade community rules.
  • If you run a filter: this page is your test suite: harden until every card round-trips to the original text.
