2.0.0-prerelease - Module fixes no tagged release yet
  • Confetti on Advancement is an actual celebration now. The burst was ~40 dust particles at scale 0.7-1.3 in a single uniform spread - close to invisible in daylight. It now opens with a centre pop, splits into three bands (fast outward ring, slow drift, and a fountain that arcs and falls), doubles the dust scale to 1.2-2.4, and trails FIREWORK shimmer behind the confetti. Default count 40 → 120, ceiling 200 → 600. Applied to both copies of FireworksFx (src/main/java and the mc26_3 override) so 26.3 does not keep the old effect.
  • StructureNotifier no longer fails silently. Its detection wrapped everything in an empty catch (Exception) {}, so a mapping change or a throwing registry lookup looked identical to "you are not inside a structure". Failures are now logged once per session, and a new Debug Log setting reports how many structure starts each chunk actually carries - which is the real question, since a multiplayer server does not send structure starts to clients at all.
  • The "Redo onboarding" button no longer lies. Its handler called toast() unconditionally after firing the bridge request, so it reported "First-run setup will run again on the next launch" even when Beacon refused the reset. The message is now the request's success notice, which only fires on an ok response; a failure surfaces the bridge's own error instead. Covered by a jsdom regression test that mocks the bridge in both states.
  • Build fix: AFKFisher referenced FishingBobberEntity, which does not exist in these mappings - the class is net.minecraft.world.entity.projectile.FishingHook (see FishingHookAccessor). All four references corrected; the code never compiled as shipped.
  • CompactMessages actually collapses duplicates now. The mixin fetched the module, tested isEnabled() and then had an empty if body, so maxCombo()/counterColor() were never called and enabling the module changed nothing - the only collapsing came from BetterChat's separate anti-spam. CompactMessages owns its duplicate detection now and appends a coloured x N badge, capped by Max Combo. New Scan Depth and Ignore Timestamps settings.
  • BetterTab no longer covers the screen. TabListPlusMixin rewrote every 13, 11 and 9 in PlayerTabOverlay.extractRenderState to 40 to make room for numeric latency - but those literals are row metrics and padding, so the whole tab list inflated several times over. The wide layout is now opt-in via Wide Ping Column (off by default).
  • SoundMuter's mute no longer sticks. Enabling it used to walk the entire sound registry and stop() every matching identifier, killing portal/beacon hums mid-loop that nothing ever restarted - so disabling could not bring them back. Muting is preventive only now: the mixin rejects new matching plays, and disabling takes effect immediately with no state to undo.
  • ItemSearch is reachable. It only accepted @search <item> while every other module answers to @ModuleName ..., so the conventional @ItemSearch wood returned "Unknown setting/subcommand", and its only setting was the toggle keybind. Modules can now handle their own subcommands (Module.onCommand), ItemSearch takes @ItemSearch <item>, and it gains Scope and Show Slots settings.
  • AFK Fisher: the description no longer credits Meteor, the bite pling is gone (with the now-meaningless Bite Alert setting), and a catch is counted once per bobber instead of once per catch path - the "Caught N fish" tally was inflated.
  • "Redo onboarding on next launch" no longer silently drops the wizard. The flags really were being cleared and reloaded; the launch check was the problem. Onboarding.onClientTick set armed = false before attempting to open the page, so if that one open failed the setup was dropped for the whole launch with nothing logged. The retry budget now covers both waits (Chromium downloading, and browser-registered-but-won't-take-the-page), the setup only disarms once the page actually opened, and every branch logs - so the next launch's log says exactly whether the reset was written or the show path failed.
  • Regenerated the module catalogue: it had drifted to 55 modules/232 settings while the Java registry held 56/234 before any of the above.

Fixed

  • The 3D onboarding intro could never actually run in a build. Beacon's loopback origin sent connect-src 'none' in its Content-Security-Policy, and three.js downloads beacon.glb with fetch() - which is what that directive governs, not media-src or script-src. Chromium therefore refused the model request before it left the browser, GLTFLoader reported a failure and the cinematic skipped straight to the welcome screen. The development harness never showed it because python -m http.server sends no CSP at all. The policy now allows connect-src 'self' (still nothing off-origin, the page never talks to the Internet), the model and soundtrack are served as model/gltf-binary and audio/mpeg instead of application/octet-stream (every response also carries nosniff), and intro3d_verify.py gained a section that checks the packaged origin instead of only the page.
  • HTML UI console output now reaches the game log. Page-side warnings and errors - including [Beacon] 3D boot intro unavailable (<reason>) and Chromium's own blocked-subresource reports - are forwarded as [Beacon][HTML UI] …, so a page that degrades no longer leaves the log silent about why.
  • The intro's beacon is textured again - it is no longer a bare grey cube. beacon.glb stores its three textures in bufferViews; GLTFLoader turns each one into a blob: URL and downloads it through fetch(). connect-src 'self' does not match blob: URLs even though the page created them, so the texture fetches were refused and the model rendered untextured. The served policy now allows blob: in both connect-src and img-src (blob: URLs inherit the page's origin and can only be created by it, so no new target is reachable). Verified against real Chromium: with the old policy the three texture fetches are CSP-refused and the shot is a plain cube; with the fix they succeed and the textured beacon renders.
  • The boot cinematic (and its audio) no longer replays on every launch. The page kept the "seen" flag only in localStorage, but the loopback origin is a fresh random port and token on every launch, so the store was empty each time. onboarding.intro-seen - which the page already posts but the bridge previously rejected as unknown - now persists a durable introSeen flag in beacon.json, the state snapshot exposes it, and the page asks for the snapshot before deciding whether to play (with a short fallback so a dead bridge cannot strand the player). @onboarding still opens the wizard, but the intro plays only once; #replay (or ?replay=1 when testing standalone) forces it again.

7.18.8 2026-10-23 · release v7.18.8 · 1 artifact
  • New movement module no-slow: decides for itself how much the item in use slows you down. 26.2 keeps the slowdown on the item itself - the USE_EFFECTS data component, read through one seam the client consults every tick it is eating, drinking, drawing or blocking - and the new LocalPlayerUseSlowMixin hands that decision to NoSlowRules, a pure decision table covered by UseSlowRulesTest. Ported from Raven B4's NoSlow with the same filter set (sword-only, disable-bow, disable-potions with thrown potions still overridable) and its one-way range: the slider only ever moves the multiplier up from vanilla's 0.2, and the default of 80% is exact vanilla parity. The description states the cost the way the desync family's does: a simulating server predicts 0.2, so the useful range is the server's to allow, not the module's.
  • New combat module keep-sprint: softens the price your own swings charge you. Vanilla multiplies the attacker's horizontal motion by 0.6 and drops sprint after every hit; AttackEntityEvent captures the motion going into the swing - the only moment the un-punished motion exists - and a tail mixin on Player.attack puts it back scaled by the slider, sprint re-raised. The default 40% restores exact vanilla motion, which makes the module's real function the kept sprint; the one-way range is Raven's, and the original's stop-sprint toggle is replaced by an explicit keep-sprint switch, since the knockback-module plumbing it served has no counterpart here. Two new mixins (LocalPlayerUseSlowMixin, PlayerAttackMixin) bring the config to nine entries and the per-class load guard covers them. Both descriptions carry the same honesty as the desync family: on Grim these are Simulation flags by design, on non-simulating servers they are free.
7.18.7 2026-10-23 · no tagged release yet
  • New network module fake-lag: holds the connection's own packets for a configurable delay - outbound (everything you send), inbound (everything the server sends), or both - releasing by age with hard flushes on teleport, damage and disconnect. Ported from Raven B4's FakeLag, whose delay engine is a shared request/handler/timeout subsystem; here each module owns its queue outright, the convention the rest of the addon already runs on. Connection-keeping packets (keep-alives, pings, chunk-batch traffic, bundles) always pass through untouched, so the hold cannot starve the world or read as a dying connection. The cost is stated in the description: released bursts read as timer anomalies on servers that count packets.
  • New network module lag-range: the same hold, but conditional - engaged only while closing on a target inside the reach band, or right after a hit landed inside the three-block minimum, and flushed the moment the exchange changes shape: a hit of your own, taking damage, a sprint restart, raising your sword, throwing a splash, opening a screen, the target leaving the band. Ported from Raven B4's LagRange with the engage shape intact; the 1.8 hurt-window hit-marking and the first-person indicator are not carried over, and the closest target scan replaces the original's targeting helper.
  • New network module backtrack: holds one target's movement packets while the withheld position is the better one to swing at - further along your aim ray than the position this client still shows, inside the reach band, on the stale side of the exchange - and releases them by age, damage, teleport or target change. The geometry lives in BacktrackMath (ray/box entry distance, the hold decision table), unit tested in BacktrackMathTest including the border-grown box edge cases. Ported from Raven B4's Backtrack with three deliberate deviations: the hold is scoped to one entity's movement packets rather than everything-but-a-whitelist (a held session cannot starve the world of chunks), the 1.8 ghost rendering is dropped, and the release clock is wall-clock milliseconds rather than tick counts. Against a lag-compensating server the effect is bounded by what it already grants; the description says so.
7.18.6 2026-10-23 · no tagged release yet
  • New combat module rod-aimbot: a right click with an uncast rod is intercepted, the closest valid player inside the cone is picked, and the cast is staged against where they will be when the hook arrives - predicted-ticks projects their observed motion through vanilla's own per-tick constants (air drag 0.91, gravity 0.08 with 0.98 drag, ground friction 0.546). Ported from Raven B4's RodAimbot with the same gates (cone, distance, invisibility, bots, teammates) and its deviations stated: the camera is never taken - the cast rotation is spoofed server-side through PreRotate, so the interaction departs before the movement packet from a rotation the server acknowledged, and the aim keeps refreshing every tick until the cast lands rather than only when the original's motion event fires. 7.18.5 2026-10-23 · no tagged release yet
  • Fixed the quit hang. Clicking Quit used to freeze the client for twenty seconds and end in a ClientShutdownWatchdog crash report with exit code -8. The cause: Baritone's cache workers are non-daemon threads parked forever in a LinkedBlockingQueue.take() inside a loop that catches InterruptedException and Throwable and keeps parking - so neither an interrupt nor a shutdownNow() can release a worker that is already parked there, and once main() returns the JVM waits on them until vanilla's watchdog force-kills the process. The fix is a shutdown reaper: a daemon thread started at addon init that watches the main thread, and the moment main() has returned invokes System.exit(0) - shutdown hooks run, the halt takes the parked threads with it, and quitting is clean and immediate. When every thread is well behaved the natural shutdown wins the race and the forced exit is a no-op on an already-halting JVM. Covered by ShutdownReaperTest (fires on death, stays quiet while watched, daemon by construction).
  • Removed fourteen dead modules after grading every one of them against the 26.2 server model. Twelve were 1.8-era packet relics that cannot function against a server-side simulation and only ever produced flags: more-carry (crafting-slot carry - servers repopulate containers on close), bungeecord-spoof (forwarding data is proxy-side; a client injection just fingerprints), kick (ESC menu exists), portal-exploits (with its two serving mixins, NetherPortalBlockMixin and ScreenMixin), reset-vl (modern anticheats do not keep reloggable violation levels), sleep-walker (the server ejects a moving sleeper), chorus-exploit (the teleport is server-authoritative), v-click-tp (client setPos rubber-bands without permission), vehicle-one-hit (vehicle health is server-side), v-ghost-hand (server raycasts), time-shift and v-anti-hunger. The other two were worse than dead: the repo's own OrphanModuleTest audit had already established that text-field-protect, extended-firework and v-ghost-hand were wired to nothing - their advertised features never ran because the mixins they waited on were never written - so those settings took space in the GUI while doing literally nothing. The orphan and inert allowlists are empty now, and the drift assertions keep them that way.
7.18.4 2026-10-23 · no tagged release yet
  • Fixed V Scaffold sending pitch steps no mouse can produce. The shared RotationGcd grid was verified against the 26.2 client bytecode and is correct: MouseHandler.turnPlayer multiplies mouse counts by f³ × 8 and Entity.turn scales that by 0.15, so the real grid step is f³ × 1.2 - exactly what the utility computes, and exactly what the network interceptor's duplicate of the formula computes. The scaffold was the fault: it imported the utility and never called it, so the staged pitch went out as the raw smoothed + wobble float, and the delta between consecutive rotations - the thing Grim's RotationPlace reachability test actually validates - landed between the grid lines (the session's two RotationPlace flags). The pitch handed to the server is now snapped onto the grid at both staging sites, measured from the rotation the server already holds, since what is validated is the step, not the absolute angle. 1.1.0 no tagged release yet
  • Works against current Beacon again. Bagley now builds against Beacon 2.0.0-prerelease (the current main, including the new Chromium web UI and onboarding work) as well as 1.9.0. No addon API used by Bagley changed between the two, so no module code was touched.
  • Fixed the build failure that broke CI. Beacon's published POM advertises its own bundled runtime libraries - the MCEF Chromium bridge (net.ccbluex:mcef, published only on maven.ccbluex.net), OkHttp and Kotlin - so resolving net.beacon:beacon-<mc>:<version> pulled in artifacts Bagley has no repository for and every Gradle configuration failed with Could not find net.ccbluex:mcef:.... The Beacon API is now consumed as a non-transitive compileOnly dependency: addons compile against Beacon's classes only, and Fabric Loader supplies Beacon's nested libraries at runtime from the installed Beacon jar.
  • BEACON_REF and the Beacon version can no longer drift. CI used to clone Beacon main and publish it to Maven Local while gradle.properties still pinned beacon_version=1.9.0, so the build only worked as long as the ref happened to be that release. The pipeline now reads mod_version out of the Beacon checkout it just cloned and exports it as BEACON_VERSION, so whichever Beacon ref is selected, the artifact Bagley compiles against is the one that checkout produced. beacon_version stays as the local-development default and is 2.0.0-prerelease.
  • Accepts Beacon >=1.9.0 <3.0.0 at runtime (fabric.mod.json), so the current 2.0.0-prerelease builds and the next 2.x releases load instead of being rejected by the old <2.0.0 range.
  • Documented that Beacon does not publish its API to the Maven package registry yet, so builds resolve it from Maven Local or -Pbeacon_api_jar; the README previously pointed at a registry copy that does not exist.
